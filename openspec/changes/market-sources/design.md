## Standards (same as every other source)
- All HTTP through `core/http.py::HttpClient` (rate limit, in-flight cap, retries, one audit event per attempt in `logs/audit.jsonl`); adapters only through `IngestAdapter`; registry-driven datasets, no hard-coded lists.
- Raw bytes kept with sha256 in the manifest; processed Parquet (zstd) with strict Arrow schemas whose types come from probes of real data; unknown columns go to `_extras` with a one-time schema-drift warning; uncastable cells go to quarantine; nothing skipped silently (anything not ingestible stays registered as `unsupported` with probe evidence).
- Audit: ingest jobs and every request are logged; `audit speed` must stay inside the caps for the new hosts too (new `BASEBALLPY_RATE_*` entries, defaults chosen from each host's published limits).
- `dlt`: the project's rule is dlt for destinations (export), our client for downloading. Decision M3 below.

## Decisions for the owner
- **M1 Scope.** DECIDED 2026-11-05 by the owner: all MLB markets (every market type), no other sports.
- **M2 Transfer route.** DECIDED 2026-11-05 by the owner: the API downloaders come first and are strongly typed into the lake; they backfill newest-first. The homelab copy is an optional speed-up, built afterwards as a one-time script that writes the same typed schemas, and dropped if it adds complexity.
- **M3 dlt.** Use our own client for downloads and dlt only for export (my pick), or build the downloaders with dlt's REST source.
- **M4 Live snapshots.** Keep the homelab collector running as is and import its rows, or move the collector into baseballpy later.

## Measurement of the homelab export (2026-11-05, DuckDB 1.4.4 postgres extension on the homelab, read-only)
- Connection: `attach 'dbname=mlb host=localhost'` works with the saved login (`~/.pgpass`); the unix socket form fails (DuckDB's libpq looks in `/tmp` and finds no password). No password was read or typed.
- Plain table scan to zstd Parquet, untyped text columns: `kalshi_candle` 3,000,000 rows in 19 s (19.4 MB, 6.5 bytes per row); `polymarket_price` 5,000,000 rows in 12 s (6.9 MB, 1.4 bytes per row). Linear guess for the whole tables: Kalshi candles 213M rows, about 23 minutes and 1.4 GB; Polymarket prices 604M rows, about 25 minutes and 0.9 GB. These come from the first rows of each table, so treat them as rough; typed columns will change the size.
- A filtered export through a `where ... in (subquery)` join on the 604M-row table was slow (51,396 rows in 406 s), so the export should be a plain ordered scan, then filter in Parquet.
- Result: the full raw history fits easily on this PC as Parquet, so the MLB filter is not needed to save space; M1 (all MLB markets) costs little.


## Findings: Kalshi public endpoints (probed 2026-11-05, no login, about 4 requests a second)
- Docs list no rate limit for unauthenticated market data (authenticated tiers are 200 to 4,800 tokens a second at 10 tokens a request), so the default cap is chosen low (4 in flight, a few requests a second) and checked by `audit speed`. Terms of use for redistributing market data are not stated on the pages read: code is shared, data is not.
- Datasets the API offers (registry candidates): `series` (188 MLB, 14 keys), `events` (14 keys, cursor paging), `markets` (44 keys; live `/markets` and archived `/historical/markets`, same shape), `candlesticks` (hourly or finer, bid, ask and traded price, volume, open interest), **`trades`** (`/markets/trades` and `/historical/trades`, 10 keys: trade id, time, yes and no price, count, taker side, block-trade flag). Trades are tick data and are NOT in the homelab tables, so the API gives more than the homelab does.
- Value shapes to type: prices are strings with up to 4 decimals (`*_dollars`), quantities strings with up to 2 decimals (`*_fp`), times ISO text, lists and dicts (`price_ranges`, `custom_strike`, `product_metadata`, `tags`, `settlement_sources`). Plan: prices `decimal(9,4)`, quantities `decimal(14,2)`, times `timestamp[us, UTC]`, enums as dictionary-encoded strings, nested values as JSON text in a typed column, anything unknown in `_extras`.
- Two stores split at `/historical/cutoff` (`market_settled_ts`, `trades_created_ts`, each its own cutoff); the downloader reads live and archived and merges by key.
- Type vocabulary: `core/schema_tools.py` has no decimal type yet; adding `decimal` names is a small framework change (Parquet stores `decimal(9,4)` as a 4-byte integer, exact and compact, and DuckDB reads it as DECIMAL).

## Slices (one commit each, gates after each)
1. Kalshi catalog: `series`, `events`, `markets` (live and archived), schema generator from probes, extractor, normalizer, adapter, tests, docs.
2. Kalshi `candlesticks` and `trades`, newest-first backfill with a resumable watermark.
3. Polymarket catalog: `events`, `markets`, `outcomes` (same pattern).
4. Polymarket `prices_history` and live snapshots.
5. Optional homelab import into the same schemas.

## Speed, threads and keys (owner request 2026-11-05)
- **Same machinery as the other sources.** All requests go through `core/http.py::HttpClient`, which keeps one in-flight cap (semaphore) and one rate cap (token bucket) per host. New hosts: `api.elections.kalshi.com`, `gamma-api.polymarket.com`, `clob.polymarket.com` (and `data-api.polymarket.com` if trades are added). Caps come from `RateLimitConfig` (`BASEBALLPY_RATE_*`, `host_rates`, `host_concurrency`), with defaults set from probes and docs, not guessed, and checked by `audit speed` (caps, retries, failures per host).
- **Job-level threads.** Work is split into many small independent jobs so the existing runner's worker threads (`resolve_concurrency`, auto up to 32) can run them side by side: Kalshi one job per market window or per batch of tickers for candles and trades; Polymarket one job per batch of token ids (the batch limit is 20). Jobs write distinct chunk files, never the same file (`ProcessedStore._refuse_name_clash`), manifest saves go through the existing locked, fast `ManifestTracker`.
- **Inside a job**, requests fan out with asyncio under the host's caps, so the in-flight cap is the one place that decides speed. The tuning step is measured: raise the caps in steps while `audit speed` shows no 429, retries or failures, then fix the default at the highest clean level.
- **Newest-first with a watermark.** Backfill starts at today and walks back in windows. A resumable watermark per dataset records the oldest day completed, so a stopped run resumes and a rerun only fetches what is new.
- **Keys.** The public endpoints used so far need no key. The homelab `~/workspace/mlb/.env` holds `KALSHI_API_KEY` and `KALSHI_PRIVATE_KEY_PATH` (variable names only were looked at; the values and the private key file were not opened or copied). Signed requests would only raise Kalshi's read budget. Plan: unauthenticated by default; an optional signer reads `BASEBALLPY_KALSHI_KEY_ID` and `BASEBALLPY_KALSHI_PRIVATE_KEY_PATH` from the user's own environment, never logged, never stored in the lake, never in the audit log.

## Rate limits measured and documented (2026-11-05)
- **Key file.** The owner added `.env.txt` (one variable, `KALSHI_TOKEN`, a 36-character value, not shown). Used as a bearer token it was rejected (`401 token_authentication_failure` on `/portfolio/balance`; `200` on public endpoints with or without it). Kalshi's documented scheme is RSA-signed requests (key id plus private key file), so the 36-character value looks like a key id that needs the private key to sign. Public market data needs no key. `.gitignore` now ignores `.env`, `.env.*`, `*.pem`, `*.key` (the file was not ignored before; it was never staged).
- **Kalshi public (`api.elections.kalshi.com`).** A step-up on `/markets?limit=1`: 5, 10, 20, 30 and 50 requests a second target for 8 seconds each gave 200 on every request, achieved 46.5 a second at the top step, p50 0.06 s, p95 about 1 s, no 429. Docs publish no limit for unsigned reads; the authenticated Basic tier is 200 tokens a second (20 requests a second at 10 tokens). Default: 20 requests a second, 16 in flight; raise only after a long run with zero 429, retries or failures.
- **Polymarket documented limits** (sliding 10-second windows, over-limit requests are throttled and queued, no 429 documented): Gamma `/events` 500, Gamma `/markets` 300, CLOB `/prices-history` 1,000, Data API `/trades` 200 (v2 `/v2/trades` 300). That is 50, 30, 100 and 20 requests a second. Measured on Gamma `/events`: 5 to 40 a second target, all 200 (35.9 a second at the top). Defaults at 80% of the lowest limit used per host: `gamma-api.polymarket.com` 24 a second, `clob.polymarket.com` 80, `data-api.polymarket.com` 16.
- Because throttled requests are delayed, not refused, `audit speed` p95 latency is the signal to watch for Polymarket; for Kalshi it is 429 and retries.

## Signed Kalshi test (2026-11-05)
`kalshi.txt` (ignored by git now) holds the RSA private key, `.env.txt` holds `KALSHI_TOKEN` (the key id) and `POLYMARKET_TOKEN`. Nothing was printed. A signed read-only call to `/account/limits` (RSA-PSS, SHA-256, headers `KALSHI-ACCESS-KEY`, `-TIMESTAMP`, `-SIGNATURE`; signed text is timestamp + method + path) returned 200: usage tier `basic`, read bucket 600 tokens refilling 200 a second (20 requests a second at 10 tokens, burst 60), write bucket 100. So signing gives no speed advantage over the unsigned rate measured earlier (46 a second clean) at this tier; higher tiers (Advanced 300, Expert 600 tokens a second) are granted by Kalshi on application. Decision: unsigned by default, an optional signer kept as a fallback if unsigned reads are ever throttled. The Polymarket token is not needed for public history and was not opened.

## Findings: Kalshi candlesticks and trades routes (probed 2026-11-05)
- **Size of the job.** 706,068 of the 900,555 catalog markets have traded volume (17.7 billion contracts); the rest have no trades. Trades come only per market (`ticker`), 1,000 per page at most; a global time window returns every sport (one hour held more than 40,000 trades, 3.8% MLB), so per-market is the right unit. Most markets need one page; the busiest World Series game side held 58,656 trades (59 pages, 19 s). Expect about 0.8 to 0.9 million trade requests and, for archived markets, about 0.9 million candle requests: roughly 22 hours at 20 requests a second.
- **Routes and the cutoff.** Trades: live `/markets/trades?ticker&limit&cursor&min_ts&max_ts` and archived `/historical/trades` (same shape, 10 keys); trades created before `trades_created_ts` (2026-09-06) are only archived. Candles: archived `/historical/markets/{ticker}/candlesticks?start_ts&end_ts&period_interval` (per market), live `/series/{series}/markets/{ticker}/candlesticks` per market and the batch `/markets/candlesticks?market_tickers=<up to 100>` (live markets only; archived tickers return an empty list; 101 tickers is HTTP 400). Intervals 1, 60 and 1,440 minutes. A one-day, 1-minute window held 1,265 candles for one game side.
- **Windows come from the lake.** A market's candle window is `open_time` to `close_time` or `settlement_ts` plus a margin, read from `kalshi_markets` (data, not a guess). Whether a market needs the archived route, the live route or both follows from its close time against `/historical/cutoff`.
- **Decisions.** Candles at 60 minutes for every market (trades rebuild any finer price, and 1-minute candles for 900,000 markets would be about a billion rows); trades for every market with volume. Work is split into one chunk per market close date (about 600 chunks): resumable, newest first, immutable once all of that day's markets are settled, parallel jobs under the shared host caps. The homelab copy of the candle table (213 million rows, probably hourly) can fill most of the archived candle backlog; the optional import is tested against the API on a sample first.

## Existing libraries and MCP servers (web search 2026-11-05, standard mode; not yet installed or run)
- **Kalshi:** an official SDK generated from the OpenAPI spec is said to exist in the Kalshi GitHub org (`kalshi-python`; the repo was not opened, so unverified); third-party clients: `pykalshi` (candlesticks, trades, with a rate-limit layer), `kalshi-py` (generated, sync and async), and an old `lowgrind/kalshi-python` (outdated login). **Polymarket:** `py-clob-client` (official, for trading), `polyoxide` (Gamma, CLOB and Data clients, `prices_history`); history is keyed by market and token ids, no bulk export tool exists, so bulk means looping markets under the rate limits. **MCP servers:** `shaanmajid/prediction-mcp` (read-only Kalshi and Polymarket tools, its own README says early stage and not for production), `joinQuantish/kalshi-mcp` (trading through Solana, unmaintained). MCP servers answer one question at a time for an AI assistant; they are not a bulk downloader.
- **Decision for the codebase (not brittle):** keep our own thin client on the shared `HttpClient`, because every other source gets its per-host rate and in-flight caps, retries, audit log and speed check from it, and a library with its own HTTP stack (requests or urllib3) would bypass all of that (`tests/test_architecture.py` allows only `core/http.py` to import `httpx`). Use the libraries and the official OpenAPI specs as the reference for routes, field names and signing (ours was checked against the documented scheme and a real 200), not as a dependency. What keeps ours from breaking when an API changes: routes in one table, types generated from live probes, unknown keys kept in `_extras` with a `schema_drift` warning, a generator rerun, and recorded-response tests. Open task: add a contract check that compares our route table with the official OpenAPI spec and flags a new or removed route (task 1.4).

## The whole homelab `mlb` database (listed 2026-11-05, after the owner asked whether it was checked)
Only the Kalshi and Polymarket tables were looked at before. The database holds far more: schema `raw` 150 tables, 207 GB (Retrosheet plays and events 33 GB, `statcast_pitch` 13.7 million rows, MLB schedule, boxscores, linescore, win probability, play by play, transactions, rosters, player stats, Lahman, **`fangraphs_*` (batting, pitching, fielding, splits, prospects and `fangraphs_projection`, 523,343 rows)**, **`bref_war_*`**, the Chadwick register), schema `core` 486 tables 24 GB, `gold` 23 tables 4.7 GB, `meta` 20 tables 1.2 GB. FanGraphs projections and Baseball-Reference WAR are not sources in baseballpy at all today, and they matter for the projection models.
