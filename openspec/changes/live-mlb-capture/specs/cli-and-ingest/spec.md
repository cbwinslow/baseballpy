## ADDED Requirements

### Requirement: `baseballpy live` Follows Every Game And Keeps Its Rows In The Lake
`baseballpy live` MUST look at the schedule (today and yesterday, UTC) every `schedule_interval_seconds` with one request per day to the MLB schedule through the shared HTTP client, start one stream task per game that is live or starts within `lead_minutes` (never a game whose state is Final, never one game twice in a run, never more than `max_live_games` at once, never while the memory governor says no), journal every poll answer, and write each game's rows to `mlb_api.game_live_events` every `commit_seconds`. Events MUST wait on one bounded queue of `queue_size` items, so that a slow sink slows polling instead of growing memory. A game stream that raises MUST be logged and restarted after `restart_backoff_seconds` at most `restart_limit` times and then reported as failed while the other games go on; a failed write MUST keep its events and retry them; a schedule error MUST be logged and the next pass MUST work; an error nobody expected (a bug) MUST be logged with its traceback, the game counted as failed and the other games go on. Stopping MUST cancel the game tasks, flush what is buffered and leave no task behind. One audit record `mlb_live` MUST count the events written. `--dry-run` MUST list the games it would follow after one schedule request per day and write no data.

#### Scenario: Games are followed, failures are bounded, a stop is clean
- **WHEN** a schedule lists live, soon, far-away and finished games, streams fail or break in the middle, the sink is slow or fails once, the schedule fails once, and the run is stopped
- **THEN** only the live and soon games are followed once each, a broken stream is restarted and a hopeless one given up after the limit with the others unharmed, polling stalls behind a full queue and all events arrive in order after the sink recovers, the failed write and schedule look are retried, no task is left, and the audit record counts the events
- Verified by `tests/test_live_supervisor.py::test_live_and_soon_games_are_followed_and_finished_or_distant_ones_are_not`, `tests/test_live_supervisor.py::test_a_game_that_starts_later_is_picked_up_when_it_comes_within_the_lead_time`, `tests/test_live_supervisor.py::test_a_stream_that_fails_is_restarted_then_given_up_and_the_others_go_on`, `tests/test_live_supervisor.py::test_a_stream_that_breaks_in_the_middle_is_restarted_and_all_events_arrive`, `tests/test_live_supervisor.py::test_the_memory_gate_holds_a_game_back_until_it_says_yes`, `tests/test_live_supervisor.py::test_at_most_max_live_games_are_followed_at_once`, `tests/test_live_supervisor.py::test_a_slow_sink_stalls_polling_instead_of_growing_memory`, `tests/test_live_supervisor.py::test_a_failed_write_is_retried_and_no_event_is_lost`, `tests/test_live_supervisor.py::test_stopping_flushes_what_is_buffered_and_leaves_no_task_behind`, `tests/test_live_supervisor.py::test_a_schedule_error_is_logged_and_the_next_look_works`, `tests/test_live_supervisor.py::test_an_unexpected_error_is_logged_loudly_the_game_is_failed_and_the_others_go_on` and `tests/test_live_supervisor.py::test_the_audit_log_records_the_run`.

#### Scenario: The command, the schedule source and the whole path
- **WHEN** the command runs with `--dry-run`, with a bad sport list, and for real with a fake supervisor, and two fixture games run through the real streamer, journal, supervisor, sink and a DuckDB query
- **THEN** the dry run lists the games and writes no data, the bad list is refused, a run turns the journal on and raises the idle limit above a rain delay, and the rows of both games are in the live view and replay from their journals
- Verified by `tests/test_live_cli.py::test_the_dry_run_lists_the_games_and_writes_nothing`, `tests/test_live_cli.py::test_a_bad_sport_list_is_refused`, `tests/test_live_cli.py::test_a_run_turns_the_journal_on_and_raises_the_idle_limit`, `tests/test_live_schedule.py::test_games_are_parsed_and_an_entry_without_a_game_pk_is_logged`, `tests/test_live_schedule.py::test_one_request_per_day_with_the_levels_and_the_date` and `tests/test_live_e2e.py::test_two_games_flow_from_the_feed_into_the_lake_and_back_out_through_duckdb`.

### Requirement: `baseballpy live` Can Broadcast Events To A JSON-Lines File And Clean Up Stored Games
With `--jsonl FILE`, `baseballpy live` MUST append every event as one whole JSON line (the typed fields of `LiveEvent` plus `season`) the moment the supervisor receives it, flushed before the next event, to a file opened for append, so that a restart continues it and a follower never sees half a line. At start, unless `--prune-days 0`, it MUST delete the live files of games that the normal ingest has stored and that are older than the limit (default 7 days).

#### Scenario: Whole lines, appended, and a start-up clean-up
- **WHEN** events are written, the command restarts, and a run starts with stored and unstored live games
- **THEN** each event is one JSON line on disk when the write returns, the file is appended not truncated, only the stored old game's file is removed, and `--prune-days 0` removes nothing
- Verified by `tests/test_live_broadcast.py::test_each_event_is_one_whole_json_line_and_the_file_is_appended_never_truncated`, `tests/test_live_broadcast.py::test_a_line_is_on_disk_when_write_returns`, `tests/test_live_broadcast.py::test_the_supervisor_broadcasts_every_event_as_it_arrives` and `tests/test_live_cli.py::test_a_run_prunes_stored_games_and_opens_the_jsonl_file`.
